검토일: 2026-09-15. 대상: 광진구 무단투기 분석 `/dumping`의 질의응답. 제품 코드·데이터·메모리는 수정하지 않았다.

## 검토 범위와 증거 구분

전체 읽기: `app/api/dumping/ask/route.ts`, `lib/dumping/context.ts`, `answer-parts.ts`, `history.ts`, `queries.ts`, `components/dumping/qa-chat.tsx`, `qa-seeds.ts`, `scripts/dumping-qa-eval.mjs`, 답변 분리 테스트. 프로젝트 메모리도 확인했다.

생성 답변의 직접 증거는 [9월 14일 저장 평가](dumping-qa-eval-2026-09-14.md)다. 해당 문서는 localhost 결과이며, 이 부록에서 새로운 프로덕션 API 호출이나 음성 시험은 하지 않았다. 코드상 결함과 저장 응답에서 관찰한 문제를 구분한다. 아래 파일·줄 번호는 검토 시점 기준이다.

## 종합 판정

“답변이 장황하고 정리되지 않는다”는 지적은 구조적으로 타당하다. 이미 프롬프트에는 짧게 쓰라는 규칙이 있지만 고정 FAQ와 생성 답변의 표현 체계가 다르고, 생성 결과의 길이·출처·형식 준수를 확인하는 장치가 부족하다. 짧게 대답하라는 지시만 추가하면 재발할 가능성이 높다.

결재라인에는 결론·판단의 한계·승인할 다음 행동이 먼저 보여야 한다. 심사위원에게는 수치의 추적 가능성·과장 억제·평가 방식의 타당성이 중요하다. 현재는 통계를 많이 설명하는 기능에 비해 의사결정에 사용할 답의 규격과 검증이 약하다.

AI 슬롭 여부는 특정 단어의 등장만으로 판단하지 않았다. QA의 주된 문제는 자평 수식어, 전혀·통째로 같은 과도한 강조, 반복되는 유보문, 괄호 안 장문 풀이, 사실·해석·제안을 한 문단에 함께 넣는 구조다. 정확한 전문용어 자체를 금지하기보다 독자의 판단 순서에 맞게 배치해야 한다.

저장 평가 `:80`의 p값 풀이 “우연히 나올 확률이 높아 연관성을 인정하기 어려움”도 쉬운 설명 과정에서 의미가 흐려진 사례다. 비전문가용 답에서는 p값 해설을 생략하고 “이번 분석에서는 연관을 확인하지 못했습니다”로 말하는 편이 낫다.

## 권장 답변 규격

별도 구청장 모드와 심사위원 모드를 크게 만들기보다 같은 답을 요약/분석근거 두 층으로 제공한다.

| 영역 | 기본 노출 규격 |
|---|---|
| 결론 | 한 문장, 60자 이내 권장 |
| 근거 | 핵심 관측·수치 2개, 각 한 줄 |
| 판단 범위 | 결론을 바꾸는 한계 1개 |
| 다음 행동 | 대책 질문일 때만 1문장. 대상·비용·담당 미확정은 그대로 표시 |
| 근거 보기 | 자료명·기준일·집계단위·정확한 수치·검증 방법 펼침 |
| 지도에서 확인 | 해당 답에서 실제 사용한 지표·장소로 이동 |

기본 답 200~300자 내외를 초기 설계 목표로 제안한다. 고정된 정답 기준이 아니라 실제 결재자·직원 사용 시험으로 조정할 값이다. 음성은 결론과 핵심 근거를 읽고, 판단을 뒤집는 한계는 반드시 포함한다.

### 예시 1: 작년보다 나빠졌나?

**민원 증가만으로 무단투기가 더 심해졌다고 판단할 수 없습니다.**

- 민원 증가분은 앱 신고에 집중됐습니다.
- 순찰 적발은 줄었지만 단속 인력 변화는 확인하지 못했습니다.

**확인할 점:** 신고 증가와 실제 발생 증가를 구분할 자료가 부족합니다.

`채널별 수치·비교 기간 보기`

### 예시 2: CCTV를 늘려야 하나?

**이번 분석만으로 CCTV 증설을 결정하기는 어렵습니다.**

- 설치에 따른 적발 감소 효과를 확인하지 못했습니다.
- 기존 장비의 위치 조정은 검토할 수 있습니다.

**다음 조치:** 후보지의 설치 조건과 이전 비용을 확인한 뒤 시범 재배치를 검토합니다.

`효과 분석과 한계 보기` `후보지 확인`

### 예시 3: 왜 다가구에서 많나?

**다가구·단독주택이 밀집한 곳에서 적발이 많지만, 그 이유는 확인되지 않았습니다.**

인구 지표를 함께 넣어도 이 관계는 유지됐습니다. 관리사무소 유무나 특정 주민 집단을 원인으로 단정할 수는 없습니다.

`주거 유형별 분석 보기`

## 검증 제안

1. **고정답과 생성답 공통 검사:** 발생/적발 구분, 인과 단정, 미확인 비용, 특정 주민 집단 지목, 자료 범위 초과, 철회된 수치의 재인용을 같은 기준으로 검사한다.
2. **형식 검사:** 결론 누락·부연 개수·문장/글자 길이·내부 코드 노출·자료 ID 유효성을 측정한다. 단순 금지어 검사는 부정문 오판 가능성이 있으므로 사람이 읽는 평가를 병행한다.
3. **질문군 확대:** 현황 판단, 비용·담당·시행 일정, 다른 구 비교, 예측의 정확도, 불리한 반론, 미확보 자료, 후속 질문, 같은 후속 질문의 다른 맥락을 포함한다.
4. **실패 흐름:** 중단 후 동일 질문, 타임아웃, 빈 답, 탭 이탈, 재시도에서 잘린 답이 완료·검증 답처럼 표시되지 않는지 확인한다.
5. **근거 추적:** 답에서 숫자를 누르면 동일 기준일·단위의 표와 분석조건이 열리는지 확인한다.
6. **사용성:** 구청장 역할과 담당자 역할 참가자가 첫 화면만 보고 결론·한계·다음 조치를 말할 수 있는지 확인한다. 읽는 시간과 오해한 판단을 기록한다.
7. **보고 방식:** 7/7 정규식 게이트 통과를 정확도 100%로 표현하지 않는다. 형식 준수율, 수치 일치, 출처 연결, 과잉추론 여부, 사용자 이해도를 나눠 보고한다.

| 숫자가 맞다는 것은 어떻게 검증하나? | 데이터 기반 수치 생성은 장점이다. 다만 생성 결과가 정확히 인용하는지와 출처 연결은 별도 검증이 필요하다. |
| 7문항 통과가 정확도 100%인가? | 특정 금지 표현의 정규식 검사 통과다. 평가 문서도 한계를 명시한다. 가독성·수치·출처·과잉추론을 구분한다. |
| 준비된 답과 AI 답이 왜 다른가? | 현재 가장 취약한 부분이다. 고정 FAQ를 생성 답과 같은 검토 기준의 승인 콘텐츠로 관리한다. |

## 유지할 장점과 실행 순서

인과 단정·CCTV 철회·효과 계산·자료 부재·집단 지목을 다루는 프롬프트는 구체적이다. 데이터에서 수치를 계산하고 정오표를 적용하며, 미확보 GPS와 판단 불가 사항을 설명하는 방향도 좋다. 직접 질문·FAQ·지도 확인·음성 요약은 결재 시연에 적합한 구성이다.

권장 순서는 **과장·모순 문구 교정 → 고정답/생성답 공통 규격 → 출처 연결 → 문맥/중단 처리 → 평가셋 보강**이다. 음성 연출이나 질문 개수를 늘리는 작업은 그 뒤에 두는 편이 낫다.
